06 — Method

How I approach it

Not a formal QA pipeline everywhere — the depth of process depends on the project. Here's what's actually behind each claim.

01

Plan it, when the project calls for it

On my capstone and IPT projects, I wrote actual test plans and test cases before testing began, mapping out the user flows I needed to cover.

02

Try to break it before I trust it

On my own Apps Script systems, I test by deliberately trying to cause failure — double-booking the same slot, submitting with missing fields, checking whether a confirmation email or calendar update actually fired, not just that the script ran without error.

03

Trace it to the real cause

When something breaks, I trace back through the logic to where it actually went wrong instead of patching the symptom I can see.

04

Check the neighbors before calling it done

I run through connected flows before closing something out, since a fix that quietly breaks something else isn't a fix.

A note on documentation

Test planning and defect tracking are documented for my capstone and IPT coursework. On my own Apps Script systems I test the same way but without formal write-ups. On the ANALI Portal, feedback went straight to the dev team as change requests over chat rather than logged defects.
